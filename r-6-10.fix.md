# Executive assessment

Based on rounds 6–10, Klyro is not fundamentally weak; it is optimized for a different execution model:

- **Klyro:** one autonomous agent with verification, repair, structured errors, and strong observability.
- **Claude Code:** a dispatcher that coordinates multiple isolated workers with flexible tools and models.

To make Klyro work like Claude Code, the main change is not adding more tools. It is building a proper **agent orchestration layer**.

The target architecture should be:

```text
Parent agent
  ├── dispatcher
  ├── task coordinator
  ├── merge manager
  └── final verifier

Child agents
  ├── separate context
  ├── restricted capabilities
  ├── optional model/budget
  ├── isolated workspace
  └── compact result returned to parent

Event bus
  └── lifecycle, status, cost, permission, verification, and failure events
```

Do not remove Klyro’s verification and event-bus features. Use them as the foundation for Claude Code-style orchestration.

> Round 8 is missing, so this plan does not evaluate the TUI/scroll implementation in detail. It does include the UI requirements created by asynchronous agents.

# 1. Main gaps, in priority order

## Priority 0 — Critical architecture and safety

These must be fixed before Klyro can safely support parallel agents.

### P0.1 — Build a real task manager

Currently `spawnAgent()` directly runs a child and waits for it. Introduce a persistent task control plane.

Create something like:

```typescript
interface TaskRecord {
  id: string;
  parentTaskId?: string;
  sessionId: string;
  agentName: string;
  status:
    | 'queued'
    | 'running'
    | 'succeeded'
    | 'failed'
    | 'cancelled'
    | 'timed_out'
    | 'blocked';

  cwd: string;
  worktreePath?: string;
  model?: string;
  depth: number;
  startedAt?: number;
  finishedAt?: number;

  changedFiles?: string[];
  result?: AgentSummary;
  error?: AgentError;
}
```

Add a new component:

```text
src/agent/task-manager.ts
```

It should own:

- task creation
- task status
- task lookup
- task cancellation
- task completion
- task timeouts
- parent-child relationships
- result storage
- task events

The current `SpawnedAgent` object should become a task handle rather than a completed result.

---

### P0.2 — Enforce agent capabilities

The existing fields are currently only declarations:

```typescript
allowedTools?: string[];
readonly?: boolean;
model?: string;
```

They must become enforced runtime policy.

Effective child tools should be calculated like this:

```typescript
effectiveTools =
  intersect(
    parentAllowedTools,
    agentDefinition.allowedTools ?? allTools,
    runtimePolicyAllowedTools
  );
```

Rules:

- A child cannot receive more tools than its parent.
- `readonly: true` must remove write and mutation tools.
- A read-only agent should not receive unrestricted `shell_exec`.
- `spawn_agent` should be removed from child agents by default.
- Explicitly deny dangerous tools even if they appear in a configuration.
- The policy layer must enforce this; tool descriptions alone are not enough.

Example profiles:

```typescript
const profiles = {
  plan: {
    allowedTools: [
      'read_file',
      'glob',
      'grep',
      'repo_map',
      'find_symbol',
      'lsp_diagnostics',
    ],
    readonly: true,
    canSpawn: false,
  },

  task: {
    allowedTools: [
      'read_file',
      'write_file',
      'edit_file',
      'apply_patch',
      'grep',
      'shell_exec',
      'run_verify',
    ],
    readonly: false,
    canSpawn: false,
  },

  review: {
    allowedTools: [
      'read_file',
      'grep',
      'git_diff',
      'run_verify',
      'lsp_diagnostics',
    ],
    readonly: true,
    canSpawn: false,
  },
};
```

---

### P0.3 — Add recursion and resource limits

Unrestricted recursive spawning is dangerous. Add limits at the runtime level:

```typescript
interface AgentLimits {
  maxDepth: number;
  maxConcurrentTasks: number;
  maxTasksPerParent: number;
  maxTotalTasksPerSession: number;
  maxRuntimeMs: number;
  maxTokens?: number;
}
```

Recommended defaults:

```text
maxDepth: 1
maxConcurrentTasks: 4
maxTasksPerParent: 8
maxTotalTasksPerSession: 32
```

A child should not spawn another child unless explicitly enabled.

The limit must be enforced even if the model directly calls `spawn_agent`.

## Priority 1 — Make spawning asynchronous

### P1.1 — Do not simply “fire and forget”

The proposed idea of injecting a delayed `tool_result` into an already-finished model request is risky.

Most model APIs expect:

```text
assistant tool call
→ tool result
→ next model request
```

Once the parent has continued to the next model request, inserting a result for an old tool call may violate the message protocol.

Use this safer contract:

```text
spawn_agent()
  → immediately returns { taskId, status: "running" }

task_get(taskId)
  → returns current status and compact result

task_wait(taskIds)
  → explicitly waits for completion

task_stop(taskId)
  → cancels the task
```

Example:

```text
Parent:
  spawn_agent(PlanAuth)
  → task_1 running

Parent:
  spawn_agent(PlanDatabase)
  → task_2 running

Parent:
  spawn_agent(PlanUI)
  → task_3 running

Parent:
  task_wait([task_1, task_2, task_3])
  → summaries for all three agents
```

Completion events can also be added to the next parent turn:

```text
Subtask task_2 completed.
Summary: ...
Changed files: ...
Status: succeeded.
```

This gives Klyro CC-like background execution without corrupting the model conversation.

---

### P1.2 — Add task control tools

Add these tools:

```text
spawn_agent
task_list
task_get
task_wait
task_stop
task_apply
```

Suggested behavior:

| Tool | Behavior |
|---|---|
| `spawn_agent` | Starts a child and immediately returns a task ID |
| `task_list` | Lists running and completed tasks |
| `task_get` | Returns one task’s status and summary |
| `task_wait` | Waits for one or more tasks |
| `task_stop` | Cancels a task and its process tree |
| `task_apply` | Applies or merges a child’s changes |

This is the Klyro equivalent of Claude Code’s `TaskList`, `TaskGet`, `TaskStop`, and related controls.

---

### P1.3 — Add cancellation and timeouts

`TaskStop` must do more than update a database record.

Use an `AbortController` and retain the child process handle:

```typescript
interface RunningTask {
  abortController: AbortController;
  process?: ChildProcess;
}
```

Cancellation must:

1. signal the child runtime;
2. terminate its process;
3. terminate descendants;
4. clean up temporary worktrees;
5. emit a `subtask.stopped` event;
6. return status `cancelled`, not `failed`.

Also distinguish:

```text
failed       → child or tool error
cancelled    → user or parent stopped it
timed_out    → runtime limit exceeded
blocked      → policy prevented execution
```

# 2. Workspace isolation

## P2.1 — Implement real worktree isolation

The current `isolation: 'worktree'` field is misleading if it does nothing.

For write-capable parallel agents, implement:

```text
parent repository
  ├── .klyro/worktrees/task_1
  ├── .klyro/worktrees/task_2
  └── .klyro/worktrees/task_3
```

Each task receives:

- a separate worktree;
- a separate branch or commit reference;
- a separate child runtime;
- the same starting revision.

Important: worktree support is more than creating a directory. It must handle:

- dirty parent worktrees;
- branch naming;
- cleanup after success or failure;
- merge conflicts;
- abandoned worktrees;
- cancellation;
- non-Git directories;
- applying changes back to the parent.

The earlier estimate of “around 50 lines” is too optimistic for a production implementation.

Recommended behavior:

```text
Plan agent:
  readonly, no worktree required

Task agent:
  isolated worktree required

Review agent:
  runs against the merged parent state

Final verification:
  runs once against the final parent state
```

If the project is not a Git repository, either:

- use a temporary directory copy; or
- prohibit concurrent write agents and allow only read-only parallelism.

Do not allow multiple write agents to modify the same cwd by default.

---

## P2.2 — Define merge semantics

Do not silently merge every child result.

A safer process is:

```text
child completes
  ↓
child result includes diff/changed files
  ↓
parent reviews or task_apply is called
  ↓
Klyro attempts merge
  ↓
conflict becomes structured error
  ↓
parent decides what to do
```

Example child result:

```typescript
interface AgentSummary {
  taskId: string;
  status: 'succeeded' | 'failed' | 'cancelled';
  summary: string;
  changedFiles: string[];
  diffRef?: string;
  tests?: {
    ran: boolean;
    passed?: boolean;
  };
}
```

A merge conflict should be represented distinctly:

```typescript
{
  category: 'merge_conflict',
  files: ['src/auth.ts'],
  retryable: false,
  message: 'Changes from task_1 conflict with the current parent tree.'
}
```

Never present a conflicted or partially merged state as successful.

# 3. Verification architecture for multiple agents

This is where Klyro can become better than Claude Code rather than merely copying it.

## Recommended verification model

```text
Parent creates baseline
  ↓
Parallel planning agents
  ↓
Parallel task agents in worktrees
  ↓
Parent reviews task summaries
  ↓
Parent merges selected tasks
  ↓
One final verification run
  ↓
Optional review agent
```

### Do not run full verification in every child by default

If five children all run the same test suite, you get:

- duplicated CPU usage;
- duplicated token usage;
- inconsistent results;
- contention for ports and temporary files;
- confusing failures.

Recommended defaults:

| Agent type | Verification |
|---|---|
| Plan | None |
| Task | Optional targeted tests |
| Review | Diff/static checks |
| Parent | Full final verification |

The parent should be the authority for the final state.

---

## Verification modes

Round 10 identifies an important problem: Klyro’s strict verification is useful for production changes but can be frustrating for exploratory work.

Add:

```text
--verify=strict
--verify=advisory
--verify=off
```

### Strict

- verification failure can trigger repair;
- introduced failures block completion;
- suitable for automated refactoring.

### Advisory

- verification still runs;
- failures are reported;
- the model may continue without entering a mandatory repair loop.

### Off

- no automatic verification pipeline;
- useful for prototypes, sketches, and exploratory work.

Also separate these categories clearly:

```text
tool_error
policy_denial
environment_failure
verification_failure
merge_conflict
agent_failure
timeout
cancellation
```

A failed `write_file` should not automatically be treated as a code verification failure.

# 4. Result and context design

## P3.1 — Return summaries, not complete child transcripts

Claude Code’s parent receives a compact child result rather than the entire child context.

Klyro should store the full child transcript separately for audit, but return only:

```text
Status
Summary
Changed files
Tests run
Important warnings
Error, if any
```

Example:

```json
{
  "taskId": "task_42",
  "status": "succeeded",
  "summary": "Updated authentication middleware to validate token expiry.",
  "changedFiles": [
    "src/auth/middleware.ts",
    "src/auth/middleware.test.ts"
  ],
  "tests": {
    "ran": true,
    "passed": true
  }
}
```

The parent can request verbose details through:

```text
task_get({ taskId, detail: "full" })
```

This prevents the parent context from being overwhelmed by child tool calls and read results.

---

## P3.2 — Implement model selection and budgets

The `model` field must either work or be removed.

Thread it through:

```text
AgentDefinition
  → TaskManager
  → child runtime
  → provider adapter
  → model API request
```

Add per-agent budget fields:

```typescript
interface AgentBudget {
  model?: string;
  maxTokens?: number;
  maxSteps?: number;
  timeoutMs?: number;
}
```

Example:

```text
Plan agents   → cheap/fast model, read-only, small budget
Task agents   → stronger model, write access
Review agents → cheap or medium model, read-only
```

If the provider cannot support the requested model, Klyro should return an explicit error. It must not silently ignore the override.

Track cost by:

```text
sessionId
parentTaskId
taskId
agentName
model
```

This preserves Klyro’s existing cost-accounting advantage.

# 5. Event bus and observability

Do not copy Claude Code’s minimal observability. Klyro’s event bus is one of its strongest architectural advantages.

Extend the event catalog with:

```text
subtask.created
subtask.started
subtask.progress
subtask.completed
subtask.failed
subtask.cancelled
subtask.timed_out
subtask.merged
subtask.merge_conflict
```

Every event should include:

```typescript
{
  sessionId: string;
  taskId: string;
  parentTaskId?: string;
  timestamp: number;
  sequence: number;
}
```

This allows you to answer:

- Which agent created this file?
- Which model consumed the most tokens?
- Which tasks failed?
- Which worktree was merged?
- How long did each worker run?
- Which policy decisions occurred inside a child?

## Fix trace persistence before enabling concurrency

The rounds mention possible JSONL corruption from concurrent sessions. Fix this with:

- one serialized trace writer per session;
- a write queue;
- unique session directories;
- sequence numbers;
- partial-line recovery;
- mandatory redaction before persistence.

Do not let every worker write directly to the same file independently.

Also ensure child events identify their task:

```json
{
  "type": "subtask.completed",
  "sessionId": "ses_1",
  "taskId": "task_4",
  "parentTaskId": "task_0",
  "status": "succeeded"
}
```

# 6. Tool catalog improvements

Klyro should not replace its structured tools with one giant shell tool. Its specialized tools are useful.

## Keep these Klyro strengths

- `run_verify`
- `apply_patch`
- `repo_map`
- `find_symbol`
- `imports_of`
- `importers_of`
- `dependencies`
- structured tool errors
- event tracing

## Add Claude Code-like composability

Add or document a small always-available core:

```text
read_file
write_file
edit_file
grep
glob
shell_exec
```

Optional aliases could help models familiar with Claude Code:

```text
Read  → read_file
Write → write_file
Edit  → edit_file
Bash  → shell_exec
Grep  → grep
```

Do not remove the Klyro names. Aliases are enough.

## MCP should come after the agent core

MCP is a real Claude Code advantage, but it should not be the first project.

When implemented, MCP tools need:

- namespace isolation;
- per-server allowlists;
- schema validation;
- permission prompts;
- timeout and cancellation;
- event-bus logging;
- secret redaction;
- network policy;
- server lifecycle management.

Do not allow arbitrary MCP servers to bypass Klyro’s policy engine.

## Network tools

Add `web_fetch` and `web_search` only as opt-in capabilities:

```text
network: disabled by default
allowedDomains: []
```

This preserves Klyro’s safer default.

## Make memory auditable

Klyro’s `memory_write` is weaker from a trust perspective because the memory store is opaque.

Add an export or visible file such as:

```text
KLYRO.md
.klyro/memory.md
```

A good design is:

```text
memory_write
  → structured Klyro memory store
  → auditable user-visible summary file
```

# 8. Recommended implementation order

## Phase 0 — Tests and safety baseline

Before changing behavior, create tests that reproduce:

1. parent blocks on `spawnAgent`;
2. child can recursively spawn;
3. `readonly` does not actually restrict tools;
4. `model` override is ignored;
5. isolation flag does nothing;
6. two child agents modify the same cwd;
7. child cancellation leaves a process running;
8. concurrent trace writes corrupt data.

This gives you a reliable before/after comparison.

---

## Phase 1 — Safe task control plane

Implement:

- `TaskRecord`;
- `TaskManager`;
- task IDs;
- status transitions;
- depth limits;
- tool capability filtering;
- `task_list`;
- `task_get`;
- `task_stop`;
- timeouts.

At this point agents may still be sequential, but the system becomes correctly modeled.

---

## Phase 2 — Asynchronous read-only agents

Enable parallelism first for read-only agents:

```text
Plan
Explore
Review
Repo analysis
```

Implement:

- immediate `spawn_agent` response;
- `task_wait`;
- completion notifications;
- event-bus task events;
- cancellation;
- per-task budget.

This avoids concurrent write conflicts while proving the scheduler.

---

## Phase 3 — Isolated write agents

Implement:

- Git worktrees;
- branch or commit tracking;
- cleanup;
- diff generation;
- explicit merge/apply;
- merge-conflict errors.

Only after this phase should parallel write agents be enabled by default.

---

## Phase 4 — Verification integration

Implement:

- parent-only final verification;
- optional child targeted tests;
- strict/advisory/off modes;
- verification after merge;
- typed child and merge failures.

The resulting workflow becomes:

```text
Plan in parallel
  ↓
Implement in isolated worktrees
  ↓
Review results
  ↓
Merge selected work
  ↓
Run one final verification
  ↓
Repair if needed
```

---

## Phase 5 — Product and ecosystem

Implement:

- real `klyro agents` CLI;
- model routing;
- visible memory;
- core tool aliases;
- MCP;
- optional web tools;
- improved task UI.

Do not begin with MCP. A plugin ecosystem will not fix a blocked or unsafe worker architecture.

# 9. Where Claude Code is stronger

## 1. Multi-agent orchestration

This is the largest gap.

Claude Code has:

- asynchronous subagents;
- task status;
- cancellation;
- isolated context;
- worktree isolation;
- model overrides;
- restricted child tools;
- a mature dispatcher pattern.

Klyro currently has the beginnings of spawning but not the control plane that makes spawning useful.

---

## 2. Parallel write safety

Claude Code’s worktree mode gives workers a safe place to edit.

Klyro’s same-cwd behavior means parallel writers can overwrite or interfere with one another.

The fix is not merely “run promises concurrently.” It is:

```text
concurrent workers
+ separate workspaces
+ explicit merge
+ conflict handling
```

---

## 3. Capability enforcement

Claude Code’s agent roles correspond to real tool restrictions.

Klyro declares `allowedTools`, `readonly`, and `model`, but according to the audit does not enforce them consistently.

This is both a correctness and security issue.

---

## 4. Agent cost and model flexibility

Claude Code can use cheaper models for planning and stronger models for implementation.

Klyro’s model field currently does not reliably reach the child provider request.

This makes Klyro’s parallelism more expensive than it needs to be.

---

## 5. Ecosystem

Claude Code is stronger in:

- MCP;
- web access;
- integrations;
- general-purpose tool composition;
- mature agent workflows.

Klyro’s specialized tools are good, but its integration surface is smaller.

---

## 6. Exploratory behavior

Claude Code generally treats failures as information for the model.

Klyro’s verification system can turn exploratory or subjective work into a failure-and-repair loop.

Verification modes will address this:

```text
strict     → autonomous correctness
advisory   → report but continue
off        → exploratory mode
```

# 10. Where Klyro is stronger

Do not remove these features while copying Claude Code.

## Klyro advantages

- Typed tool errors;
- policy and defense-in-depth;
- verification and repair;
- structured event bus;
- per-step and per-tool accounting;
- replayable trace design;
- code-graph tools;
- token-efficient repository exploration;
- explicit audit history.

The best final product is not “Claude Code with a different name.”

It should be:

> Claude Code-style orchestration with Klyro-style verification, security, and observability.

---

# 11. Acceptance criteria

Klyro should not claim Claude Code-like multi-agent support until these tests pass:

1. Parent can start three agents without waiting for each one.
2. Task status becomes visible immediately.
3. Parent can continue issuing tool calls.
4. Child agents cannot recursively spawn by default.
5. Read-only agents cannot edit files or execute mutation-capable shell commands.
6. Model overrides actually reach the provider.
7. A user can stop a child and its entire process tree.
8. A timeout produces `timed_out`, not a generic failure.
9. Parallel write agents receive separate worktrees.
10. Parent files remain unchanged until an explicit merge/apply step.
11. Merge conflicts are reported as structured errors.
12. Child transcripts remain separate from the parent context.
13. Parent receives a compact result summary.
14. Final verification runs against the merged parent state.
15. Child lifecycle events appear in `trace.jsonl`.
16. Trace writes remain valid under concurrent tasks.
17. Secrets are redacted before trace persistence.
18. `klyro agents` is no longer a stub.
19. Strict, advisory, and disabled verification modes work.
20. A failed child can be retried, ignored, or replaced by the parent.

The most important implementation rule is:

That is the difference between “several promises running at once” and a real Claude Code-style orchestration platform.
