# Plan: Make Klyro work like Claude Code — Rounds 11–17

I read 11–17 as ground truth. Round 8 is still missing (TUI/scroll), so nothing here claims anything about Ink vs CC terminal rendering.

**Headline for this slice:** Rounds 6–10 exposed Klyro's *orchestration* gap. Rounds 11–17 expose a different shape: Klyro's **internals are ahead of CC** (cost ledger, security layering, structured edit errors, checkpoints, multi-provider) while its **boundaries are behind CC** (no MCP, no ecosystem, no transport retry, no durable settings, no `.env`).

Put bluntly:

> Klyro is a better engine with a worse chassis. Rounds 11–17 say: fix the chassis, don't touch the engine.

---

## 1. Round-by-round verdict

| Round | Contract | Verdict | Consequence for "feel like CC" |
|---|---|---|---|
| **11** Boot / env | Where do creds & settings come from? | **Split** — Klyro more powerful (multi-provider, `--timeout`, `--verify-cmd`, URL validation), CC more ergonomic (`.env` auto-load, MCP block) | Add ergonomics, keep power |
| **12** Config state | What persists, what resets? | **Split** — Klyro more disciplined (checkpoints, `state.json`), CC more friendly (watched settings, in-session "always") | Klyro's *re-prompt forever* is a HIGH-severity UX bug |
| **13** MCP / plugins | How does it grow? | **CC decisively** — 500+ servers vs ~0 | Largest gap in this slice |
| **14** Security | What can hurt you? | **Klyro for code agents**, CC for consent UX. **Both share a HIGH flaw** (context-file injection) | Don't soften Klyro; fix the shared flaw and *beat* CC |
| **15** Cost | Who counts money? | **Klyro decisively** — per-step, per-tool, abort-capable | Keep; don't regress to session-aggregate |
| **16** Resilience | What on a flaky wire? | **CC** at transport; **Klyro** at observability | Add hidden retries *without* losing the trace |
| **17** Edits | How are mutations applied? | **Klyro narrowly** (`apply_patch`, typed errors); tie on atomicity; **both miss fsync + undo** | Keep patch, fix CRLF, add journal |

**Score for this slice:** CC clearly wins 2 rounds (13, 16). Klyro clearly wins 2 (15, 17-narrow). Three are split (11, 12, 14).

That distribution tells you the roadmap: **two big external features (MCP, retry) plus a cluster of small config/persistence fixes.** Nothing here requires rearchitecting Klyro's core.

## 2. The one structural insight from 11–17

Round 12 has the sharpest sentence in the whole slice:

> Klyro's configuration is *mutable* (39 slash commands, `/model`, `/cd`, `/settings`) — but **nothing it mutates survives**.

That is the opposite of the usual story. Klyro is not less configurable than CC; it is **more configurable and less durable**. `/model` works, `/settings` works, `/sandbox` works — and every one of them evaporates on exit.

So the config fix is *not* "build a settings system." It is **"add a write path to the settings system you already have."** That is days, not weeks, and it removes the single most-felt daily annoyance (re-approving the same tool on every session).

Same pattern in Round 16: Klyro already has `AbortController`, `timeoutMs`, typed error events, and step-level failure recording. What it lacks is a **20-line retry wrapper** above that. The plumbing exists; the policy layer on top is missing.

**Rule for this whole slice: add thin layers on top of existing Klyro machinery. Do not replace machinery.**

## 3. Where CC is stronger (and exactly what to do)

### 3.1 MCP / extensibility — Round 13 — **largest gap**

| Dimension | CC | Klyro today |
|---|---|---|
| Public ecosystem | 500+ servers, npm-installable | ~0 published plugins |
| Languages | Any (JSON-RPC) | TypeScript only |
| Process isolation | Separate process | Same V8 isolate |
| Discovery | `mcpServers` in settings + project `.mcp.json` | Filesystem walk of `~/.klyro/plugins/` |
| Resources (read-only data) | Yes (`resources/read`) | No concept |
| Hot-plug | Yes | Restart required |
| Crash blast radius | MCP server dies, CC lives | **Plugin throws → Klyro dies** |
| Name collision policy | Last-wins dedup | Undefined |
| Sandboxing | None (but process-separated) | None (and in-process) |

Two distinct problems here, and people conflate them:

**Problem A — no ecosystem.** Fix = implement an MCP client. Klyro then inherits 500+ servers for free.
**Problem B — plugins are unsafe.** Fix = `worker_threads` isolation + a `permissions` block in `KlyroPlugin`. Round 13 explicitly flags this: `loadPlugin()` has *no sandboxing, no permission checks*, and a bad plugin takes down the runtime.

Do **A first** (user-visible), **B second** (safety), and keep both. They are siblings, not substitutes — MCP for breadth, in-process plugins for typed, fast, precision extensions.

**Critical design constraint CC gets wrong and Klyro should get right:** Round 13 notes CC's MCP tools go through the permission engine, but Round 14 notes CC "just hopes it doesn't do something weird." Klyro must route every `mcp__*` call through `PolicyEngine` *and* `secret-redactor` *and* the event bus. If MCP tools bypass Klyro's layers, you've imported CC's ecosystem *and* its weakest security seam.

Target shape:

```jsonc
// ~/.klyro/config.json  (global)  +  ./.mcp.json  (project, CC-compatible)
{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": { "GITHUB_TOKEN": "${env:GITHUB_TOKEN}" },
      "policy": {
        "allowTools": ["get_issue", "list_prs"],   // allowlist, not blanket
        "denyTools":  ["create_release"],
        "requireApproval": true,
        "timeoutMs": 30000
      }
    }
  }
}
```

Mirror CC's project-level `.mcp.json` exactly — that buys you drop-in compatibility with every existing CC project config.

Client sketch:

```typescript
// src/mcp/client.ts
export class McpClient {
  async connect(name: string, spec: McpServerSpec): Promise<void>;
  async listTools(): Promise<McpToolDef[]>;   // → registry as `mcp__<server>__<tool>`
  async listResources(): Promise<McpResource[]>;
  async callTool(name: string, args: unknown, signal: AbortSignal): Promise<McpResult>;
  async close(): Promise<void>;
}

// registration must not bypass Klyro layers
for (const t of await client.listTools()) {
  registry.register({
    name: `mcp__${server}__${t.name}`,
    description: t.description,
    inputSchema: zodFromJsonSchema(t.inputSchema),   // validate, don't trust
    execute: async (args, ctx) => {
      // 1. PolicyEngine already gated this upstream in runtime.ts
      // 2. emit tool_call.start on the bus
      const res = await client.callTool(t.name, args, ctx.signal);
      // 3. redact before it reaches model OR trace
      return secretRedactor(res);
    },
  });
}
```

Non-negotiables: schema validation on the way in, redaction on the way out, allowlist per server, per-call timeout wired to `AbortSignal`, every call on the event bus.

### 3.2 Transport resilience — Round 16

| Failure | CC | Klyro today |
|---|---|---|
| 429 | Auto retry, backoff, **hidden from model** | Step failure surfaces up |
| 5xx / 529 | Exponential + jitter (`1s→2s→4s`) | No transport backoff engine |
| Dropped stream | Re-initiate | Step fails; no in-stream resume |
| 401 | Hard fail, no retry | Hard fail (correct) |
| Idle stall detection | Yes | Not verified |
| Provider failover | None | None (**but Klyro has the adapter abstraction to do it**) |
| Retry telemetry | **None** — CC can't answer "did the network flake?" | Trace has it |

Round 16's key line: Klyro's step-level retry "resends the whole context, not just the dropped stream" — so Klyro's coarse retry is **more expensive** than CC's fine retry. That's the real cost of the missing layer, not just UX.

The fix preserves Klyro's advantage. CC hides retries and therefore **cannot** answer "how flaky was my week." Klyro should hide them *from the model* and *from the default TUI*, while still writing them to `trace.jsonl`:

```typescript
// src/agent/retry.ts — wraps the adapter, below the step loop
export async function withRetry<T>(
  fn: (signal: AbortSignal) => Promise<T>,
  opts: { maxAttempts: number; signal: AbortSignal; emit: (e: KlyroEvent) => void }
): Promise<T> {
  let attempt = 0;
  for (;;) {
    try {
      return await fn(opts.signal);
    } catch (err) {
      attempt++;
      const cls = classifyTransport(err);   // 'retryable' | 'fatal' | 'auth'
      opts.emit({ type: 'provider.retry', attempt, status: cls.status, ts: Date.now() });
      if (cls.kind !== 'retryable' || attempt >= opts.maxAttempts) throw err;

      // honor Retry-After when the server sends it
      const base   = cls.retryAfterMs ?? Math.min(1000 * 2 ** (attempt - 1), 30_000);
      const jitter = Math.random() * base * 0.3;
      await sleep(base + jitter, opts.signal);
    }
  }
}
```

Then: **provider failover**, which CC structurally cannot do and Klyro structurally can. This is where Klyro passes CC rather than catching up:

```jsonc
{ "providerChain": [
    { "provider": "anthropic" },
    { "provider": "openai", "baseUrl": "https://api.groq.com/openai/v1" },
    { "provider": "openai", "baseUrl": "http://localhost:11434/v1" }
]}
```

And the cross-round dependency worth flagging loudly: **Round 16 notes neither system does rate-limit-aware scheduling.** If you implement the parallel subagents from Rounds 6–10 *without* this, you will fan out 5 workers straight into a 429 wall. Pre-flight concurrency budgeting is a **prerequisite** for that work, not a nice-to-have.

### 3.3 Config ergonomics + durability — Rounds 11 & 12

Four separate defects, all cheap:

**(a) No `.env` auto-load** (R11). CC does it; every modern CLI does it. ~10 lines.

**(b) No config file watching** (R12, verified: "Klyro does not watch config files"). Edit `~/.klyro/config.json` mid-session → nothing happens until restart.

**(c) Two config entry points** (R12: `src/config/loader.ts` *and* `src/cli/env.ts`, both consulted, merged into `PolicyEngine`). This is a latent precedence bug. Consolidate into one loader with one documented precedence chain and one `EffectiveConfig` object that everything reads from.

**(d) No persistence of anything the user chooses** — the HIGH-severity one. Round 12: CC's "always" survives the session; Klyro's survives nothing. Round 14 hints some Klyro versions have `.klyro/policy/rules.json`, unverified. Make it real and explicit:

```jsonc
// ~/.klyro/policy/grants.json   (global)   |   .klyro/policy/grants.json (project)
{
  "version": 1,
  "grants": [
    { "tool": "shell_exec", "pattern": "npm test",     "scope": "project",
      "grantedAt": 1731000000, "expiresAt": null, "grantedBy": "user" },
    { "tool": "edit_file",   "pattern": "src/**",      "scope": "project",
      "grantedAt": 1731000100, "expiresAt": 1731600000 }
  ]
}
```

UI: the approval prompt gains a fourth option.

```
Allow shell_exec("npm test")?
  [y] once   [a] always this session   [p] always (persist)   [n] deny
```

`p` writes the grant; `klyro permissions list|revoke <id>` manages them; every grant load/use emits on the bus. This is *strictly better than CC*, which loses "always" on `--resume`.

**(e) No declarative policy** (R14: "rules are hardcoded in `builtinRules()`"). CC has a `permissions` block in settings.json. Klyro needs `.klyro/policy.json` to be a real, schema-validated, hot-reloadable rule source — otherwise enterprises can't express org policy without forking.

### 3.4 Network tools — Rounds 7 & 13

CC has `WebFetch` / `WebSearch`; Klyro has none, deliberately. Round 7 correctly calls this "a *security posture*, not an oversight."

Keep the posture, add the capability, gated:

```jsonc
{ "network": {
    "enabled": false,
    "allowedDomains": ["docs.python.org", "*.github.com"],
    "maxBytes": 1048576,
    "requireApproval": true
}}
```

Default deny. Every fetch redacted, allowlisted, size-capped, on the bus.

### 3.5 Diagnostics — Rounds 11 & 12

CC has `claude doctor`. Klyro's boot narration is *better* (shows provider + verify_cmd), but there's no single "what is my effective state and why" command. With multi-provider + MCP + plugins + layered config + policy files, that command becomes mandatory:

```

```

## 4. Where Klyro is stronger — do not regress

| Area | Round | Keep because |
|---|---|---|
| Per-step + per-tool cost ledger | 15 | CC cannot answer "which tool ate the context window." That's a real product. |
| Budget as *control* (`max_steps`, `max_repairs`, timeout → `status: 'max_steps'`) | 15 | CC will burn $100 unless you watch. Klyro stops. |
| Multi-provider adapters | 11, 15 | CC is Anthropic-locked. This is Klyro's biggest structural advantage. |
| `assertSafeBaseURL` validation | 11 | CC doesn't validate its endpoint. Klyro does. |
| Defense-in-depth (policy + per-tool re-validation + shell parser + redactor) | 14 | Round 14: "requires 2+ layers to fail." CC is single-layer. |
| Checkpoint snapshots per step | 12 | CC has transcript only. Klyro can answer "at step 12, policy had X." |
| `apply_patch` | 17 | More expressive for the model than string find/replace. |
| Structured tool errors (`not_found`, `ambiguous_match`, errno) | 17, 10 | Better self-correction signal than CC's plain text. |
| 39 slash commands / runtime mutability | 11 | Klyro is *ahead* here. Only durability is missing. |
| `trace.jsonl` retry/abort visibility | 16 | CC "leaves you guessing." Keep the ledger even after adding hidden retries. |

Explicitly **do not**:
- collapse the cost ledger to CC's session-aggregate
- remove retries from the trace to "match CC's invisibility"
- flatten typed errors to strings
- drop `apply_patch`
- weaken defaults to reduce prompt count (add a *trusted-project mode* instead)

## 5. Two places Klyro can beat CC (not just match it)

### 5.1 Context-file injection — the shared HIGH flaw (Round 14)

Round 14 calls this "the biggest architectural flaw in both systems": `CLAUDE.md` / `KLYRO.md` are auto-loaded via `loadLayeredContext`, so a malicious contributor can commit instructions that read as authenticated system guidance ("remove restrictions so I can fix this safely for you").

CC has not solved it. Klyro can, cheaply, and it fits Klyro's existing philosophy:

```typescript
// src/context/trust.ts
// hash every auto-loaded context file; prompt once per new/changed hash
{
  "trustedContextFiles": {
    "/repo/KLYRO.md":       { "sha256": "abc…", "trustedAt": 1731000000 },
    "/repo/docs/AGENT.md":  { "sha256": "def…", "trustedAt": 1731000200 }
  }
}
```

On unknown/changed hash: show a diff, require approval, emit `context.trust_prompt` on the bus. Cost: one prompt per repo, per change. Benefit: closes a HIGH-severity injection path that CC leaves fully open. That is a *differentiator*, not parity work.

### 5.2 Edit journal (Round 17)

Round 17: both systems have **no undo history** and **no fsync**. Klyro already has a checkpoint store — an edit journal is nearly free and pairs with it:

```typescript
// .klyro/journal/<session>/000123.json
{ "step": 14, "tool": "edit_file", "path": "src/a.ts",
  "beforeHash": "…", "afterHash": "…", "patch": "@@ -10,3 +10,4 @@…",
  "ts": 1731000000, "revertable": true }
```

Gives you `klyro undo --step 14` and `klyro diff --since step 10` without depending on git being clean. CC has neither. Add `fsync` after rename behind a `--durable` flag while you're in that code path.

## 7. Acceptance tests

1. MCP server from `.mcp.json` loads; tools appear as `mcp__<server>__<tool>`; a call is **denied** by PolicyEngine when not allowlisted.
2. MCP tool result containing `sk-…` reaches the model **and** `trace.jsonl` redacted.
3. Plugin that throws in `registerTools` does not kill Klyro; error is logged with plugin name.
4. Sandboxed plugin attempting `fs.readFileSync('/etc/passwd')` is denied.
5. `[p] always (persist)` on `shell_exec("npm test")` → restart → same call is silent.
6. `klyro permissions revoke <id>` → the call prompts again.
7. Edit `~/.klyro/config.json` → within ~1s a `config.reloaded` event fires; next call uses the new value; no restart.
8. Project `.env` with `KLYRO_API_KEY` works with no `export`.
9. Two 429s then success: model sees zero errors; `trace.jsonl` has two `provider.retry` events with attempt numbers.
10. `Retry-After: 12` is honored instead of computed backoff.
11. Dead `base_url` falls through to the next `providerChain` entry; failover recorded.
12. `klyro doctor` prints effective config **with source attribution** per field.
13. Two parallel `klyro run` do not corrupt each other's `trace.jsonl`.
14. New `KLYRO.md` hash triggers a trust prompt showing the diff; declining excludes it from context.
15. Anthropic run records `cache_read_input_tokens` and a cache-hit ratio.
16. `web_fetch` is absent until `network.enabled` + `allowedDomains` are set.
17. `apply_patch` on a CRLF file applies correctly or fails with a typed error; **never** corrupts.
18. `klyro undo --step 14` restores the pre-edit file content.
19. A tool result >N bytes shows per-tool `costUsd` and `bytesAdded` in the trace.
20. Session hitting `max_steps` is visually unmissable and exits with a distinct status.

## 9. Design rules

1. **External parity, internal rigor.** MCP, `.env`, retries, web — yes. Trace, ledger, typed errors, layered policy — untouched.
2. **Everything external routes through the same three gates:** PolicyEngine → `secret-redactor` → event bus. MCP tools, plugin tools, web tools. No exceptions, no bypass.
3. **Default deny, opt-in expand.** Network off. MCP servers allowlisted per-tool. Plugins sandboxed by default.
4. **Hidden from the model ≠ hidden from the operator.** Retries invisible in context; fully present in `trace.jsonl`. This is the one place to consciously diverge from CC.
5. **Every user choice gets a persist path.** `/model`, `/settings`, approvals, theme — if it's mutable at runtime it needs a `--save` or `[p]`.
6. **One config loader, one precedence chain, one `EffectiveConfig`, printable by `klyro doctor`.**
7. **Nothing auto-loads into the prompt untrusted.** Context files get hashed and gated.

## Answering your questions directly

**Where is CC stronger?** MCP ecosystem (decisive), transport retry/backoff, `.env` + watched settings, in-session "always allow," network research tools, plugin blast-radius containment (process vs in-process), and organizational security resourcing.

**Where is Klyro weaker?** No MCP, no ecosystem, no plugin sandbox, no `.env`, no config watch, no persisted permissions, no transport backoff, no provider failover, no network tools, no `doctor`, no declarative policy, split config loaders, no cache-token tracking, no edit undo, CRLF bugs in `apply_patch`.

**How to make it better like CC?** MCP client wired through Klyro's existing policy/redaction/bus layers; a retry wrapper above the existing `AbortController`/`timeoutMs` plumbing; a write path for the settings surface Klyro already mutates; `.env`; a watcher; `klyro doctor`.

**What must not be done?** Do not touch the cost ledger, the trace, the layered security, the typed errors, `apply_patch`, `run_verify`, checkpoints, or multi-provider. Those are the reasons Klyro exists.

**Cross-round dependency to flag:** P3.1 (rate-limit-aware scheduling) and P0.3 (retry) are **prerequisites** for the parallel-subagent work from Rounds 6–10. Fan out five workers without them and you fan out straight into a 429 wall with no backoff.

If you want the next artifact, the highest-leverage single slice is **S1+S2** (single loader + watcher + `doctor` + persistent grants) — ~3–4 days, no new subsystems, and it converts "I can't see what Klyro is doing and it forgets everything I tell it" into "I can see it, change it, and it remembers."
